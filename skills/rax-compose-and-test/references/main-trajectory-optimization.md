# 合并 main 以后：从多路点到速度连续的独立候选

这是 Piper v0.5→v0.6 的实测方法，属于完成函数演练、合并 main 之后的优化；不是 Franka 上游规定的通用轨迹算法。上游依据仍是 [workflow.md](workflow.md) 中的函数契约、按需观察、组合 main 与新摆位测试。

## 先区别三个层次

1. **v0.4：函数合并。** Python 顺序调用，底层仍逐动作规划、交接、到位与持稳。
2. **v0.5：命令合并。** 准备/接近和搬运/下降分别成为多路点 ActionChunk，中间不再交接，但每段五次曲线在路点速度为零，因此仍会顿一下。
3. **v0.6：有选择的速度衔接。** 指定非接触路点允许非零速度通过；闭爪、试抬结果、释放等有结果依赖的边界继续保留。

不把“少调用几次函数”“一次下发”与“物理运动连续”混为一谈。Piper 仍接收30 Hz位置目标，数值曲线连续不保证电机侧跟踪速度完全连续；要看SDK回执与实测反馈。总时间、连续程度、成功率分别记录。

## 先按时间线定位，再改对应层

一轮至少记录：主函数阶段、MCP请求/返回、owner前动作确认、预检开始/结束、等待新反馈、策略轮询、首末SDK回执、到位/持稳完成、RGB/FFS/Gemini调用。用同一时钟做差；不要把main时间与启动/收尾混比。

| 现象与已确认原因 | v0.6 方法 | 不能删掉的条件 |
|---|---|---|
| 动作已结束，下一动作仍等约0.2–0.7秒 | Owner状态签名加入`rax_motion`，active_request变化立即发布 | 真实回执与唯一Owner交接，不靠猜测空闲 |
| 刚完成持稳，取图又重新等同一个窗口 | 同请求、同Owner、新鲜状态匹配，完成后≤0.5秒时复用已完成0.3秒/≥4样本的证据 | 过期、身份改变、状态不一致重新持稳；第一次捕获不一致后，第二次必须新窗口 |
| 只做试抬RGB对比却触发头部深度 | 动作后观察默认RGB；先普通规则，未解决事实需要深度时再请求 | 初始度量定位仍需新深度；不能以到位单独证明持杯 |
| 闭爪拆成15.6→5.6→3mm，每段都交接持稳 | 单独的完整闭合工具，从≤20mm开度单调闭到3mm，臂固定 | 原10mm/s、力设置、到位判断不变；普通张爪工具仍保留原10mm步长 |
| 试抬结束后才求解搬运目标 | 根据本轮定位及入杯候选提前求解，试抬通过后核对实际状态再复用 | 同目标/Owner/几何；预测关节误差≤0.01rad，目标FK误差≤1mm；不符则从实测状态重算 |
| 一条多路点命令仍每点停下 | 用五次Hermite在指定空载准备点与杯垫上方转折衔接速度 | 悬停/入杯、闭合、试抬确认、最终支撑高度/释放停点仍保留 |

各阈值是当前设备选定参数，不是其他机器默认值。几何误差和容差单位必须明确。

## 曲线修改必须进入实际执行检查

用相邻同向割线速度的调和平均产生路点速度，初始比例0.3；反向的关节置零。保持精确路点、路点加速度为零、整段首尾速度为零。若偏离原关节直线超过0.01rad，降低过渡速度重新计算，不放宽该界限。

依次检查解析速度/加速度极值、30 Hz float32实际下发速度/加速度、新曲线安装几何与桌面碰撞、各下发间隔端点及中点的FK工作区。保留按SDK进度检查实测反馈，不能用整个任务的包围盒代替当前路径检查。每个关节仍可能因方向反转而过零；“速度衔接”不等于恒速。

闭爪工具应明确区分“完整闭合行程”与“任意大开合”，不要把所有夹爪工具的步长上限一并提高。闭爪完成之后仍是试抬验证，不直接把搬运与闭爪拼接。

## 这次碰到的实现问题

- 初版曲线偏离原路径超过0.01rad：按偏离量缩小切向速度，重新检查整条曲线；没有加大允许偏差。
- NumPy标量直接作为IK参数被接口拒绝：在工具边界明确转换为Python float/list；提前规划失败应保留原因，不能悄悄把“写了预规划”当作实际命中。
- 复制Owner后，`XPolicyLab`自指向仍指回旧目录：运行契约拒绝跨checkout导入。隔离Owner的自别名必须指回新Owner，`real_world`为实际独立副本；不能只改一个脚本路径。
- 控制台无法连接：旧v0.5仍持有Prepare会话和相机。先查会话身份及是否空闲，通过原控制台Stop释放，再只读Connect；不是网络故障，也不该删除锁或直接kill硬件Owner。
- 仅在后端改RGB默认还不够：任务层`current_depth`仍会无条件再次取深度，必须检查完整调用链。
- 实测第一轮仍有一次初始视觉调用，整轮比v0.5慢；优化局部交接不保证每轮总耗时更短。

## 证据与仍待验证项（2026-11-11）

139项宿主离线检查通过，另有原路径真实FCL/FK/ActionChunk契约验证。两轮v0.6源码一致、报告成功、Stop确认、记录未标人工帮助：main 58.178/46.311秒，Gemini 1/0次；两轮试抬与最终判断均无Gemini，搬运预规划均复用。

v0.5闭爪5.29/5.50秒→v0.6约3.14/3.09秒。前动作ack累计等待约2.23/2.16秒→v0.6轮询时几乎无需再等（约10微秒合计的测量分辨率，不能解释成物理停止延迟）。试抬末SDK到搬运首SDK间隔从2.310/2.642秒变为1.585/1.652秒，仍不是零间隔。

这些是不同场景的描述性记录，不是同摆位A/B因果证据。原路径接近16.30秒、搬运下降3.367秒的下发时长没有被压缩；主要改变速度过零点及边界等待。保留首次准备前的预检、首次定位/必要视觉调用，以及接触边界的真实持稳。完整载荷/线缆/未知环境扫掠、移动Stop延迟和更广摆位泛化未因此验收。

## 给后续使用者的交接

- 保存原main和冻结版本；独立候选、独立Owner源码及Web端口，配置写入版本身份。
- 控制器、后端、Owner发布逻辑必须一起核对；只复制`controller.py`不会获得相同效果。
- 新摆位初始自动定位；不把历史离线路点或图片变成运行坐标。
- 先离线验证失效路径，再由现场监督者启动一次；失败保留报告，不自动重放。
- 报告至少标记完整闭合次数、持稳复用、深度调用、搬运预规划命中、blend_indices、阶段/总时间及Gemini次数。
- 代码与复现见仓库 `demos/piper-blue-cup-v0.6/README.md`；skill复制到本机后，可从原仓库取demo。复现依赖已适配Piper/XPolicy runtime，不宣称从干净Franka仓库可直接接机。
