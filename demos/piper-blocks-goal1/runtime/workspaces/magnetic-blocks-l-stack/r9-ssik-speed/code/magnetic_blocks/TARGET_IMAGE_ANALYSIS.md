# 输入另一张目标图片后自动搭建：进阶分析，尚未实施

当前 v0.2.1 仍只执行“红橙并排，绿放红上”的结构。它用当前桌面观测计算位置，支持的是初始摆位变化；并没有实现目标结构变化。换一张图片不会自动改变 main 的搭建目标。

Franka 原生 autonomous-control 要求把可复用动作与场景输入分开、用当前观测适应摆位，逐函数调通后组合 main，并在不同摆位检验。它没有提供一个保证任意目标图片都可搭建的通用编译器。下面是基于这条方法的任务扩展设计，不是声称上游已有此功能。

来源：[Franka autonomous-control](https://github.com/robot-agent-exploration/rax/blob/real/franka/agent_skills/task/autonomous-control/SKILL.md)、[本人的合并 skill](https://github.com/CoCoMatrix/rax-skills/blob/main/skills/rax-compose-and-test/SKILL.md)。

## 建议先达到的能力边界

先限定为桌面现有红、橙、绿三块约 60 mm 的立方积木，直立、完整面支撑，支持并排、换颜色叠放、简单塔形和台阶。目标图片主要指定相对关系，整组结构在桌面的绝对位置由可达性选择。悬空、斜放、拱桥、双支点跨放、新物体及不可见背面结构另行探索。

“新初始摆位”“新目标结构”“新物体/操作类型”是三个不同的泛化层次，需要分别验收。

## 需要补齐的内容

| 环节 | 当前已有 | 需要补充 |
| --- | --- | --- |
| 目标图片解析 | TASK 写死红橙并排、绿在红上 | 一次视觉解析输出物体身份、上下支撑、左右/前后邻接、朝向、可见/不确定关系。图像像素位置不是机器人目标 XYZ |
| 桌面初始感知 | 头部 RGB-D 定位、同轮三维目标保留、腕部辅助 | 与图片物体对应；测每块实际尺寸/高度、中心和偏航。若颜色相同，需要位置/特征区分身份 |
| 目标坐标生成 | 红块为固定参照；绿在红上 | 从实际桌面平面和积木尺寸生成目标槽位，选择整组结构的平移/朝向；图上“左”须约定为操作者方向或图案自身坐标 |
| 任务顺序 | main 固定先移动橙、后移动绿 | 按支撑关系先底层后上层，检查目标位是否被占、夹指退路是否被后放积木挡住，必要时安排临时位置 |
| 可复用动作 | 已演练接近、闭合、试抬、搬运、下降、释放和退开 | 将 orange/red/green 硬编码的角色改为 moving_object、support_object、neighbor_objects；保留颜色作为感知身份 |
| 几何与抓法 | 本次约 60 mm 积木、50 mm 闭合目标及特定前后抓取 | 按实际积木与放置邻接方向选择抓取轴，保存物体相对夹爪的关系。不同尺寸不能沿用同一闭合宽度与包络 |
| 路径可行性 | 单步 IK/CAD、载荷/邻块采样检查 | 在执行前核对完整计划的进入、搬运、下降、张爪和退路，以及后续堆高后的可达性。范围内不等于朝向可达 |
| 结果与异常 | 阶段报告、定性判断、首错返回 | 按目标关系检查“大体并排/在谁上面/是否明显倾斜”；记录哪块已放好，异常只恢复相关步骤，不能整段盲重放 |

现有 `plan_base_placement`、`refresh_stack_support`、`stack_target`、`LoadedChecks`、`LowerChecks`、`StackReleaseChecks` 都含有当前三色结构的专用假设，不能只把 main 的颜色字符串换掉就宣称通用。尤其当前红块不移动；若目标要求红块在顶层，需要红块抓取和上层放置的实际演练。

## 如何仍保持 RAX 原生流程

不需要另建一套框架。继续在独立任务工作区保存目标图片、一个简单的目标关系文件、本轮场景测量、执行步骤和报告即可。

拟议的数据流：

```text
目标图片 ──一次语义解析──> 目标关系
当前三路观测 / 头部深度 ──> 实际物体状态
两者结合 ──> 目标槽位、抓法、支撑依赖和动作顺序
可行性检查 ──> main(ctx, plan) 调用已演练函数
阶段回执 / 必要观察 ──> 更新物体状态，检查目标关系
```

视觉模型可以在任务开始时分析图片一次；主 Agent 负责研发阶段新增函数的探索和演练。整段自动执行时，根据生成的计划调用普通 Python 函数；正常动作之间无需重新问主 Agent。只有关系解析不明确、出现新操作类型或执行异常时才需要额外推理，不能预先承诺每张图都零模型调用。

比如目标从“绿在红上”换成“橙在绿上、红在旁边”，需要改变的是支撑关系、先后顺序、抓取对象及目标位，不应为每张图片另写一个固定 main。若只是三块换了初始摆位，目标关系不变，则重测场景后执行同一计划模板。

## 关于图片和标定

一张倾斜拍摄的图片未必能区分前后接触、隐藏积木或实际间距。可从明显支撑/邻接关系生成合理布局，不把无法确定的背面内容臆测为事实；确有歧义时补一张侧视图或一句目标关系说明。图案只要求相对结构时，不必复现照片的透视或绝对毫米位置。

若继续以头部标定深度生成 base-frame 目标，腕部用于 RGB/光学深度辅助，腕部手眼标定不是实现第一阶段的必备前置条件。若想在头部遮挡后直接用腕部点生成机器人坐标，则需补可靠的手眼外参；不能把 optical XYZ 当成 base XYZ。还应核实各积木实际高度、夹指碰撞包络与桌面模型，避免误差在多层堆叠中累积。

## 递进验证路径

1. 先验证本次 L 形合并版在多个初始摆位下整段成功，建立基线。
2. 把对象/支撑角色参数化，用同样三块练习颜色互换后的 L 形。
3. 加入明确的新目标：反向 L、三块并排、两层台阶。每种新增抓放关系按 RAX 逐函数演练。
4. 再接目标图片解析，先离线验证识别出的关系和动作顺序，再测试未见过的图片与初始摆位。
5. 分别记录目标解析正确率、计划可执行率、整段成功率、人工介入、阶段/总耗时、模型次数。单次人工帮助成功不能归为无人整段成功。

最应先补的是**参数化的抓放函数和目标关系表示**。更大的模型、减少检查或增加几张示例图，不能替代这两项。
